# Accessibility

Radix NG primitives provide roles, ARIA attributes, keyboard navigation, and focus management for
the behaviors documented on each primitive's page. Your application supplies the markup, labels,
content, and visual design.

## How we decide what semantics to use

We start with native HTML, add ARIA where needed, and use APG and WCAG to guide behavior and checks:

1. **Native HTML first.** Prefer elements with the required semantics and behavior, such as
   `<button>`, `<label>`, and `<fieldset>`. See the
   [first rule of ARIA use](https://www.w3.org/TR/using-aria/#firstrule).
2. **[WAI-ARIA](https://www.w3.org/TR/wai-aria-1.2/).** Add roles, states, and properties for custom
   widgets where native semantics do not provide them.
3. **[WAI-ARIA APG](https://www.w3.org/WAI/ARIA/apg/).** Follow its keyboard and focus guidance for
   the relevant widget pattern. APG is authoring guidance rather than a normative standard.
4. **[WCAG 2.2](https://www.w3.org/TR/WCAG22/).** Use its success criteria to guide checks for
   keyboard operation, focus order, labels, errors, and name/role/value.

Each primitive's **Accessibility** section maps its implementation to the applicable APG pattern
and WCAG criteria, and documents its keyboard interactions.

> WCAG conformance depends on how you assemble and style the primitives. The building blocks are
> designed against these references and tested for documented keyboard and focus behaviors;
> check the assembled interface in your application, including with relevant assistive technologies.

## Labels, keyboard, and focus in your application

- **Provide accessible names.** Associate visible labels with their controls. Use the documented
  [Field](?path=/docs/primitives-field--docs) or [Label](?path=/docs/primitives-label--docs) anatomy,
  or the part's documented ARIA labeling attributes.
- **Preserve keyboard behavior.** Follow each primitive's host-element and nesting requirements,
  and check its Keyboard Interactions table when adding custom handlers.
- **Check focus in context.** Opening, closing, and composing overlays can change where focus moves.
  Verify the documented behavior with your content and any custom autofocus handlers.
- **Style visible states.** Supply visible focus indicators and check contrast, disabled states,
  and error messages in the finished interface.

## Visually hidden text

Use Tailwind's `sr-only` for text that should remain available to assistive technology:

```html
<button type="button">
  <svg aria-hidden="true"><!-- Icon --></svg>
  <span class="sr-only">Add to favorites</span>
</button>
```

Use Angular's `[hidden]` binding to hide an element visually and from the accessibility tree. For
simple native form serialization, use a named `<input type="hidden">`; controls that need browser
validation or autofill should use their primitive's native form integration.

For runtime warnings, structural errors, and Angular DevTools, see
[Guides/Debugging](?path=/docs/guides-debugging--docs).
