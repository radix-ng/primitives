# Popper logical sides (Base UI `useAnchorPositioning` parity)

the positioner `side` input accepts the logical `inline-start` / `inline-end` alongside physical `top`/`right`/`bottom`/`left`; they resolve to `left`/`right` by text direction (a `dir` input on the wrapper falling back to the enclosing direction provider). The public placement state **echoes the kind requested**: `data-side` / `placedSide()` and the `OffsetFunction`'s `side` stay logical when a logical side was passed — even after a collision flip re-sides the popup — and stay physical for a physical request, so a `[data-side="inline-start"]` style rule is direction-agnostic and per-primitive popups/arrows inherit the echo through context with no change. The arrow, transform-origin, and menu safe-polygon geometry read a **separate internal `physicalPlacedSide`**, because their `OPPOSITE_SIDE` / geometry maps need the real physical side a logical `data-side` would break (any downstream consumer that reads `data-side` as a physical value must use this channel instead). This is the last item of the popper audit; `disableAnchorTracking` and the submenu POPUP-vs-DROPDOWN split remain deferred.
