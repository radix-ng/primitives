# ADR 0050: Preserve Menu sessions across mixed input

- Status: Accepted
- Date: 2026-11-12
- Decision owners: Radix NG maintainers
- Related: ADR 0048, ADR 0049, `menu`, Context Menu, Menubar

## Context

Separate keyboard, mouse and touch suites did not compare input changes within one session.
Enter/Space on a touch-opened submenu entered its items instead of toggling it closed. A touch
press on an arrow-opened child closed it immediately, unlike the pin's first-press promotion.
Moving into a touch-opened child with an arrow also incorrectly changed its VoiceOver ARIA policy.

## Decision

Reuse Root's accepted reason and request metadata, without a second interaction store. Root accepts
promotion from list-navigation to trigger-press through the same cancelable transaction as hover
promotion. The first touch press promotes an arrow/hover child and keeps it open; the next toggles
it closed. Keyboard activation toggles an already press/navigation-opened child and promotes a
hover-opened one. Click-only activation follows the same policy. Forward-arrow entry remains a
navigation request.

SubTrigger preserves its opening keyboard/ARIA classification when an arrow enters an already open
child. Clear that classification only after Root accepts a touch request. A canceled promotion
retains the previous reason, keyboard navigation and aria-expanded policy. Focus and return focus
continue through the existing Popup/Floating Focus Manager, with no forced rendering or focus loop.

Scroll locking follows the input that began the session. Touch promotion of a mouse-hovered popup
does not turn it into a new touch opening. Closing and opening again by touch starts a fresh policy:
a small popup permits page scrolling, while an effectively viewport-wide popup locks it. Keep the
existing separate session touch flag; do not derive scroll policy from the latest request type.

Seventeen pinned scenarios compare mixed selection, successive/retained sessions, hover promotion
and cancellation, LTR/RTL submenu entry, keyboard toggling, canceled child promotion and small/wide
scrolling. Inputs use actual Playwright mouse, touch and keyboard APIs. Hybrid checkpoints compare
original callback metadata for the latest request; attachments retain the entire native timeline.
No event type, trust, focus or primitive state is rewritten by a fixture.

## Native event adaptations

Keyboard activation routing and its exact event pairs are superseded by [ADR 0051](0051-menu-native-host-activation.md), which verifies native application click handlers and link navigation. The remaining hover/focus adaptations still apply.

Keep the directive's original keyboard event instead of constructing a click to match a React
utility. Exact native-keyboard-events pairs record keydown versus click, including the pin's
untrusted Space click generated by useButton. The physical input remains trusted in both fixtures.
Selection, request reasons, focus, ARIA and completion are still compared independently.

Exact native-hover-events pairs retain Pointer Events entry versus the pin's mouse movement entry,
and safe-polygon movement versus mouse leave on canceled root promotion. These are source-event
contracts, not new state differences. macOS WebKit's existing native-button-focus category also
covers hover/touch promotion. Every pair is scoped to its exact checkpoint/engine, with macOS-only
focus scope. A changed or disappeared pair fails; there is no normalization or broad acceptance.

## Verification and remaining scope

Menu defines 139 scenarios / 417 planned comparisons: 369 executable, 48 touch capability skips.
The 34 new comparisons run in Chromium/WebKit; Firefox touch contexts remain unsupported. Focused
Menu unit/browser checks cover toggling, veto, source event identity and ARIA. Public examples cover
Enter/Space closing and forward-arrow entry after a tap. Selected Context Menu/Menubar composition
checks guard their shared Menu implementation.

After reopening, observe the same settled placement/checkpoint used on the first open before wheel
input. This permits native layout/effect work to finish; it does not wait for a particular lock
implementation, retry wheel input or change reference state.

Local validation starts with changed scenarios and one engine, then supported engines and affected
consumer checks. Full suites remain available for uncertain scope, failures, CI or an explicit
request. This changes the local workflow, not CI coverage or required checks.

Additional API/lifecycle combinations, native/custom-host activation and real-device/AT audits
remain separate work; emulation does not certify assistive technology.
